第 3 章我们追踪了 Agent Loop 的完整运转过程。其中最关键的一步是"调用模型"——Loop 把消息发给 LLM，拿到回复，根据回复决定继续还是停止。

但当时我们用了一行代码就跳过了：

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
const stream = streamSimple(model, context, options);
```

这行代码看起来平平无奇。但如果你打开 `packages/ai/src/api/` 目录，会发现不同协议的请求构建、流式响应和兼容处理分布在多份实现中。**一行调用的简洁背后，是整个 AI 抽象层的精心设计。**

这一章就来拆开这一行代码：Pi 怎么做到用同一个接口调用 不同供应商提供的模型？如果你想接入一个新模型，需要做什么？

---

## 一、问题：同一段对话，不同模型要"翻译"成不同格式

先说清楚要解决什么问题。

Agent Loop 要调用模型，但市面上有几十家模型供应商——Anthropic（Claude）、OpenAI（GPT）、Google（Gemini）、AWS Bedrock、Mistral……每家都有自己的 API 规范，用不同的字段名、不同的数据结构来描述同一件事情。

这个差异有多大？我们看一个最简单的例子。假设用户对 Agent 说了一句话：

> "帮我读一下 main.ts"

这条消息在 Pi 内部是这样存的（统一格式）：

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
{ role: "user", content: "帮我读一下 main.ts", timestamp: 1748697600000 }
```

但要把这条消息发给不同模型，就必须"翻译"成各家要求的格式。同样是这一句话，四个 Provider 要求的长相完全不同：

**Anthropic（Claude）**——这里展示内容块数组写法，每项带 `type`；纯文本也可使用字符串：

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
{ role: "user", content: [{ type: "text", text: "帮我读一下 main.ts" }] }
```

**OpenAI（GPT）**——格式看起来差不多，但字段语义有细微差异（比如工具结果消息的处理方式完全不同）：

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
{ role: "user", content: "帮我读一下 main.ts" }
// 但如果消息里包含工具结果，OpenAI 要求单独的 { role: "tool" } 消息，
// 而 Anthropic 把工具结果合并到 user 消息里
```

**Google（Gemini）**——字段名从 `content` 变成了 `parts`，结构更扁平：

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
{ role: "user", parts: [{ text: "帮我读一下 main.ts" }] }
```

**Bedrock（AWS）**——在 AWS 自己的结构上又包了一层：

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
{ role: "user", content: [{ text: "帮我读一下 main.ts" }] }
// 注意：Bedrock 的 text 没有 type 字段，和 Anthropic 不一样
```

**连最简单的纯文本消息都有四种写法。** 字段名不同（`content` vs `parts`），结构不同（有的要 `type` 字段，有的不要）。

<Diagram file="/assets/260925-ch04-provider-formats.svg" caption="四个 Provider 的消息格式差异" id="260925-ch04-provider-formats" />

**配图说明**：这里比较协议格式；同一供应商也可能提供多种 API。

### 不只是消息格式——四个维度全都不一样

消息格式只是冰山一角。Provider 之间的差异是全方位的，主要在四个维度上：

| 维度 | 差在哪 | 举个例子 |
|------|--------|---------|
| **消息格式** | 同一条消息，字段名和结构不同 | Anthropic 用 `content[]`，Google 用 `parts[]` |
| **流式传输** | 模型的"逐字返回"机制不同 | SSE、SDK 事件流和 WebSocket 等传输路径需要适配 |
| **思考模式** | "让模型深度思考"的参数完全不同 | Anthropic 用 `thinking.budget_tokens`，OpenAI 用 `reasoning_effort` |
| **缓存控制** | "标记不变内容"的方式不同 | Anthropic 打 `cache_control` 标记，Bedrock 插入 `cachePoint` 节点 |

每个维度单独看都不复杂，但这些维度再乘以不同 Provider 的能力差异，组合起来的差异量是巨大的。

现在问题来了：**Agent Loop 只有一行 `streamSimple(model, context)`，它不可能为每个 Provider 写一套不同的逻辑。那它怎么应对这么多差异？**

## 二、解法：翻译公司里，先分清客户经理和翻译员

用翻译公司作比喻：客户交来一段话，前台找到合适的人，翻译员负责读懂对方的协议，最后按统一格式交回报告。

但这里有个容易混淆的角色：**Provider 是供应商，API 是协议**。一家供应商可能提供几种协议，几家供应商也可能都提供 OpenAI 兼容接口。把“每家一个翻译器”写死，复用的机会就丢了。

### 第一层：Models 和 Provider，负责把请求交给对的人

v0.87.1 的推荐入口是 `Models` 集合：它管理 Provider，按模型所属供应商路由请求。Provider 再负责自己的目录、认证和流式行为，底下可以复用 API 实现。

```
应用 / Agent Loop
    │ models.streamSimple(model, context, options)
    ▼
Models：按 model.provider 找到 Provider
    ▼
Provider：目录、认证、请求行为
    ▼
API 实现：把 TranscriptContext 翻译成线上协议
    ▼
供应商响应 → 统一的 AssistantMessageEventStream
```

模型对象的两个字段因此不能混为一谈：`provider` 回答“由谁提供服务”，`api` 回答“按什么协议交谈”。同一 API 适配器可以被不同 Provider 复用，而它们的认证和请求头仍各自管理。

<Diagram file="/assets/260925-ch04-translation-company.svg" caption="Models、Provider 和 API 适配器的分工" id="260925-ch04-translation-company" />

### 一个还在使用的入口：/compat

读默认 coding-agent 源码时，你仍会遇见从 `@earendil-works/pi-ai/compat` 导入的 `getModel`、`stream` 和 `streamSimple`。这个兼容入口保留全局模型目录、API 注册表及原有调用方式；它不是主入口的同名导出。

兼容入口也先 `normalizeContext()`，内置模型会优先走相应的内置 Provider；自定义 API 注册仍有注册表分派路径。因此不能把现在的整个入口概括成“查一次 model.api 就完了”。

| 使用场景 | 入口 |
|----|----|
| 新建独立模型调用应用 | 主入口的 `createModels`，配合 `providers/*` 工厂 |
| 需要全部内置供应商 | `providers/all` 的 `builtinModels()` |
| 阅读旧调用方式、保持现有代码可用 | `/compat` 的全局 `getModel`、`streamSimple` 等 |
| 嵌入 coding-agent，复用它的配置与认证 | `ModelRuntime` + `createAgentSession()` |

### 第二层：先把上下文变成统一 transcript

从应用看，`Context` 仍可写成 `{ systemPrompt, messages, tools }`。这是方便调用者的简写。Provider 收到的却是 `TranscriptContext`，提示词和工具声明已经放进 `messages` 中的 system 消息。

```typescript
// 教学简化：省略外围定义，展示数据形状或关键步骤
// 类型关系示意，省略其他字段
Context
  → normalizeContext()
  → TranscriptContext { messages: Message[] }
  → Provider / API 实现
```

为什么多一道门？假设会话中途换了系统指令，或卸载一个工具。只看当前配置，你知道“现在是什么”，却不知道“何时变的”。transcript 能记录这些变化，让恢复会话和切换分支有依据。第 6 章讲数据结构，第 10 章讲如何落盘。

自定义 API 实现不能再直接读取 `context.systemPrompt` 和 `context.tools`，应根据需求使用 `getCurrentSystemPrompt(context.messages)`、`getCurrentTools(context.messages)` 或 transcript 解析工具。

### 第三层：标准报告——统一事件流

输入统一以后，输出也要统一。不管底下用哪个 SDK，Agent Loop 接收的都是以下事件族：

```
start
  text_start → text_delta → text_end
  thinking_start → thinking_delta → thinking_end
  toolcall_start → toolcall_delta → toolcall_end
done 或 error
```

在这个版本里是 12 种事件，但记住族群比背数字更有用：文字、思考、工具调用都可以逐段到达，最终必须收尾。

**并非每个事件都有 `partial`。** start 和内容增量事件带处理中消息；done 带最终 `message`；error 带失败的 `error` 消息。请求准备阶段就失败时，还可以没有 start，直接以 error 结束。消费者如果假定第一条永远是 start，就会漏掉这类错误。

### 翻译器内部：五步骨架仍然成立

<Diagram file="/assets/260925-ch04-translator-5-steps.svg" caption="翻译器内部 5 步骨架" id="260925-ch04-translator-5-steps" />

1. 准备客户端和认证。
2. 把 transcript、工具和选项转换成供应商请求。
3. 发出请求。
4. 把响应中的文本、思考和工具片段转换成 Pi 事件。
5. 发送 done 或 error，并结束事件流。

真正费力的仍是第 2、4 步。比如 Anthropic 的 tool_use 要变成 Pi 的 toolCall，Google 的 parts 要变成文字、图片或函数调用块；工具调用 ID、思考签名和中途切换模型时的兼容处理，也都在这个边界完成。

`StreamFunction` 的入职要求则是：接收 `Model`、规范化的 `TranscriptContext` 和选项，返回 `AssistantMessageEventStream`。这是一份协议契约，而不是要求所有翻译器继承某个基类。

## 三、怎么用：从调用到接入新模型

### 场景一：只调用需要的供应商

下面是一个完整示例。先配置 `ANTHROPIC_API_KEY`；依赖版本固定到本书的 0.87.1。

```typescript
// 完整示例；依赖版本见本书修订记录
import { createModels } from '@earendil-works/pi-ai';
import { anthropicProvider } from '@earendil-works/pi-ai/providers/anthropic';

const models = createModels();
models.setProvider(anthropicProvider());
const model = models.getModel('anthropic', 'claude-sonnet-4-5');
if (!model) throw new Error('模型不在已注册目录中');

const stream = models.streamSimple(model, {
  systemPrompt: 'Explain things clearly.',
  messages: [{ role: 'user', content: '什么是 Agent Loop？', timestamp: Date.now() }],
}, { reasoning: 'high' });

for await (const event of stream) {
  if (event.type === 'text_delta') process.stdout.write(event.delta);
  if (event.type === 'error') console.error(event.error.errorMessage);
}
const result = await stream.result();
console.log(result.stopReason, result.usage);
```

为什么不用默认把所有供应商都导进来？只注册需要的 Provider，目录和依赖边界更清楚；API 实现还能懒加载。若你的产品本来就要支持全部内置供应商，用 `builtinModels()` 即可。

`stream()` 接收协议专属选项，`streamSimple()` 接收统一的思考级别等选项，由适配器映射。两者不是“一个有功能、一个没有功能”，也不保证后一种实现永远逐层调用前一种公开函数。

### 场景二：嵌入 coding-agent

独立的 `Models` 不会自动理解 coding-agent 的全部本地配置。`ModelRuntime` 才负责把它们组起来：凭据、`models.json`、内置与扩展 Provider、模型目录和可用性。

```typescript
// 完整示例；依赖版本见本书修订记录
import { createAgentSession, ModelRuntime } from '@earendil-works/pi-coding-agent';

const modelRuntime = await ModelRuntime.create();
const model = modelRuntime.getModel('anthropic', 'claude-sonnet-4-5');
if (!model) throw new Error('模型未找到');

const { session } = await createAgentSession({ modelRuntime, model });
try {
  await session.prompt('解释当前项目的结构。');
} finally {
  session.dispose();
}
```

这里把同一个 runtime 交给会话，选模型和真正发请求才能沿用同一份配置。`getModel()` 查到模型并不代表认证一定有效；可用列表还要通过 runtime 的可用性检查。

默认 `createAgentSession()` 会替你创建 runtime；手工传入主要用于自定义认证、配置或共享组合。扩展里保留的 `ctx.modelRegistry` 是兼容视图，不应再把旧 `ModelRegistry.create()` 当成 SDK 的组装中心。

### 场景三：接入新模型，先判断差异在哪一层

| 新服务的情况 | 需要做什么 |
|----|----|
| 已经在内置目录里 | 配认证，选择模型 |
| 提供现有兼容协议，只是 URL、模型名或头不同 | 用 `models.json`，或组合自定义 Provider |
| 有自定义目录、OAuth 或请求行为 | 实现/注册 Provider，复用已有 API 实现 |
| 线上消息协议也不同 | 编写 API 流实现，把响应变成统一事件 |

大多数企业网关并不需要从头写翻译器。先核对接口格式、认证和模型元数据，把变化限制在真正不同的地方。写新协议时，还必须测试取消、请求准备失败、部分 JSON、工具结果回放等路径；“能返回一句话”还不是完整适配。

## 四、【进阶】翻译器内部：流式解析与思考模式方言

### SDK 帮了忙，不等于适配器没有工作

v0.87.1 的 Anthropic 实现使用 `@anthropic-ai/sdk`，通过 `client.beta.messages.create(...).asResponse()` 发请求。旧版讲解里“Anthropic 没有 SDK，只能自己解析原始 SSE”的说法已经不成立。

协议解析和语义转换是两回事。SDK 能把响应变成结构化事件，但 Pi 仍需决定：这段文本属于哪个 content block？工具参数还没输出完时如何维护 partial？何时记录 usage？哪一种 stop reason 对应 toolUse？

所以读这一层时，先找请求构建，再找事件分派，最后找收尾和 catch。沿这三个位置读，比从一个上千行文件第一行一路背到末尾更容易理解。

### 思考级别是一把共同刻度，不是统一 token 预算

```
off → minimal → low → medium → high → xhigh → max
```

AI 层的 `ThinkingLevel` 不含 off，`ModelThinkingLevel` 在它的基础上加 off。Agent 对外提供的思考设置也允许 off。不同层的类型名字很像，读签名时要看清导入来源。

<Diagram file="/assets/260925-ch04-thinking-levels.svg" caption="思考级别、模型能力与协议参数的映射" id="260925-ch04-thinking-levels" />

这个顺序表达的是请求意图，**不是每一格固定消耗多少 token**。Anthropic 可能使用预算或自适应思考，OpenAI 使用 effort，Google 使用自己的 thinking 配置；相同的 high 不意味着计算量相同。

模型的 `thinkingLevelMap` 声明支持情况：null 表示不支持，字符串映射到供应商的值。`xhigh`、`max` 需要模型显式声明支持；无推理能力的模型只暴露 off。

`clampThinkingLevel()` 遇到不支持的级别，先向上找，再向下找。这个回退只是“选一个模型接受的级别”，不是质量或成本保证。产品需要展示可选项时，调用 `getSupportedThinkingLevels(model)`，不要写死七个按钮。

## 五、【进阶】缓存控制与错误处理

### 缓存：省下重复计算，不省略请求内容

对话越长，每次请求的历史前缀越大。缓存让服务端复用相同前缀的计算；应用仍然发送当前所需上下文，不能因为“上次发过”就自行删掉消息。

Pi 用 `cacheRetention: "none" | "short" | "long"` 表达意图，各 API 再翻译为实际参数：Anthropic 的 cache_control、Bedrock 的 cachePoint，以及 OpenAI 的 cache key 和模型相关 retention 参数。

注意“模型相关”这几个字。0.87.1 的 OpenAI Responses 会根据兼容元数据选择旧的 `prompt_cache_retention`，或新的 `prompt_cache_options`；不能给所有模型都硬塞 `24h`。OpenAI 兼容接口也不自动等于支持 Anthropic 缓存标记。

把它们想成三种记号：在内容上贴便签、在流里插路标、给请求带一个便于路由的编号。记号的形状不同，目的都是提高可复用前缀的收益。

每次构建新的 JavaScript 对象不会单独破坏缓存；真正重要的是发出的内容、顺序和服务端策略。命中还受有效期和模型支持影响，因此“字段没变”不是必中的承诺。第 9 章会再讲 coding-agent 的缓存保温，以及它与压缩的区别。

### 错误：流内失败与调用层异常要分开

适配器通常把请求失败转换成 `error` 事件，同时在最终 assistant 消息里设置 `stopReason: "error"` 或 `"aborted"`。这样 Loop 能沿统一通道知道这次响应没有完成。

但不能把它扩大为“调用任何入口都永不抛出”：无效配置、缺少认证等准备错误可能在直接调用时同步抛出；自定义 `streamFn` 也必须遵守自己的契约。Agent Loop 要求它把请求/模型/运行时失败编码成流，调用者则仍要处理启动与配置异常。

底层收到 error 或 aborted 会结束这一趟运行。要不要重试、是否属于上下文溢出、需不需要压缩，是上层根据错误分类做的决定，不是“错误进了流，循环就永远不停”。

## 六、回到那一行代码

现在再看 `streamSimple(model, context)`：

```
应用表达意图
  → 上下文归一化
  → Models / Provider 选择服务与认证
  → API 实现翻译消息、思考级别、工具与缓存参数
  → 供应商响应
  → 统一事件流
  → Agent Loop 处理消息和工具
```

“翻译公司”的比喻仍然成立，只是现在我们分清了客户经理和翻译员。**Provider 管供应商的事情，API 管协议的事情，Loop 管执行的事情。**

值得带走的三个设计方法：

1. **协议先于实现。** 统一输入与流事件，让不同 SDK 都能接入。
2. **语义刻度与模型能力分开。** high、long 表达调用意图，具体支持范围交给模型元数据。
3. **把变化留在正确边界。** 换地址不必重写协议，换协议不必重写循环；但每一层的错误和兼容边界都要测试。
